# CUST-GSTIN-UNIQUE — completion report

**Branch:** `fix/customer-gstin-unique` (from `main` 590aeb1) · **Migration:** `drizzle/0036_customer_gstin_unique.sql`

## The problem in plain English

The app already had a friendly error ready ("A customer with this GSTIN already exists in your account.") and a rule in
`CUSTOMER_MAPPINGS` that shows it when the database refuses a duplicate GSTIN. But the database rule itself
(`customers_biz_gstin_uq`) was never created, so the refusal never happened: the Add/Edit Customer form quietly let one
business save two customers with the same GSTIN. Found while building bulk import (PR #60).

## What changed

| File | Change |
|---|---|
| `lib/db/schema/customers.ts` | Partial unique index `customers_biz_gstin_uq` on `(business_id, gstin) WHERE gstin IS NOT NULL`. |
| `drizzle/0036_customer_gstin_unique.sql` (+ snapshot, journal) | Generated by `drizzle-kit generate`; one `CREATE UNIQUE INDEX` statement. |
| `lib/db/constraint-names.ts` | Comment updated (the name is now real, not "created later"). |
| `tests/integration/cust-gstin-unique.test.ts` | 6 PGlite tests (below). |

No action code changed: `create-customer` and `update-customer` already pass `CUSTOMER_MAPPINGS` to `toThrowable`, which
now turns the database's `23505` on this index into `DUPLICATE_CUSTOMER_GSTIN` with the message on the `gstin` field.

### What the rule means

- Same business, same GSTIN → refused.
- Different businesses, same GSTIN → allowed (each business has its own customer list).
- Customers with no GSTIN (blank → stored as `NULL`) → unlimited, untouched ("partial" index).

## Checks done

1. **Existing duplicates on bm_dev:** none. bm_dev currently has 0 customer rows, so there was nothing to merge or delete.
   Also checked: 0 rows with lower-case/padded GSTINs, 0 empty strings.
2. **Upper-case normalisation:** not needed. The validators (`lib/validations/common.ts` `gstin`, used by the form and
   import) store GSTINs upper-cased, blanks become `NULL`, and there are no old rows to fix. If a future database ever has
   legacy rows, the `CREATE UNIQUE INDEX` simply fails loudly on a duplicate instead of hiding it — run the duplicate query
   below first.
3. **Bulk import (PR #60, `run-bulk-import.ts`):** it already skips GSTINs that exist and does all inserts in one
   transaction. If a duplicate slips in through a race, the index now makes the insert fail and the whole import rolls back
   (nothing half-imported). It calls `toThrowable(error)` without mappings, so the user would see the generic error in that
   rare race — see follow-up.
4. **Migration applied to bm_dev** (`pnpm db:migrate`), index verified in `pg_indexes`.

```sql
-- duplicate check (run before applying to any database with real data)
SELECT business_id, gstin, count(*) FROM customers WHERE gstin IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1;
```

## Tests (`tests/integration/cust-gstin-unique.test.ts`)

1. Index exists with the exact name the mapping uses, and is partial.
2. `createCustomer` duplicate in the same business → `DUPLICATE_CUSTOMER_GSTIN`, message on `gstin`, no DB internals leaked, only one row saved.
3. `updateCustomer` changing to another customer's GSTIN → same code; re-saving a customer with its own GSTIN still works.
4. Same GSTIN in two businesses → both saved.
5. Three customers without GSTIN → all saved.
6. Raw duplicate insert → Postgres `23505` on `customers_biz_gstin_uq`.
